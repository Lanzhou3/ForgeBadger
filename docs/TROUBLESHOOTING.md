# ForgeBadger First-User Trial Troubleshooting

> Status: first-user local beta trial support | Date: 2026-05-10

This guide covers the first-user trial path in
[TRIAL-RUNBOOK.md](TRIAL-RUNBOOK.md). It is not a public release guide.

Use the table by matching the visible symptom first, then checking the likely
cause before applying the smallest fix or workaround.

## Core Dependencies

| Symptom | Likely cause | Check | Fix or workaround |
| --- | --- | --- | --- |
| `forgebadger doctor` reports `terminal tmux_missing`, the terminal never starts, or attach fails on macOS/Linux/WSL. | `tmux` is not installed, is below the supported version, or cannot create sessions in this environment. | Run `forgebadger doctor`, `tmux -V`, then create/list a disposable tmux session. | Install tmux 3.2 or newer using the host package manager. `start`/`init` may offer a fixed command in an interactive non-CI shell; the default is No and only explicit `y`/`yes` runs it. If tmux still fails, use a normal local shell that permits pty and tmux. |
| `forgebadger doctor` reports `terminal psmux_missing` on native Windows. | psmux is absent from `PATH`; WSL and native Windows have separate runtimes. | In PowerShell run `forgebadger doctor`, `Get-Command psmux`, and `psmux -V`. | Install the official package with `winget install --id marlocarlo.psmux --exact --source winget`, then open a new terminal if PATH has not refreshed. `doctor` never installs anything. |
| `forgebadger doctor` reports `terminal psmux_outdated` on native Windows. | Installed psmux is older than ForgeBadger's minimum 3.3.8 control-mode baseline. | Run `psmux -V`; ForgeBadger requires 3.3.8 or newer. | Run `winget upgrade --id marlocarlo.psmux --exact --source winget`, then restart the shell and rerun `forgebadger doctor`. |
| `forgebadger start` or `forgebadger init` shows an install command, then exits non-zero without starting or initializing. | The prompt was declined/defaulted to No, stdin is not a TTY, CI is set, no allowlisted Linux package manager was found, installation failed, or PATH has not refreshed. This fail-closed result is expected. | Confirm no Gateway/Web child was started and no runtime/project state was created, then run the read-only `forgebadger doctor`. On Linux, supported detection is limited to `apt-get`, `dnf`, `yum`, `pacman`, `zypper`, and `apk`. | Run the displayed command yourself, or rerun interactively and explicitly enter `y`/`yes`. npm postinstall never installs system software. If ForgeBadger reports `restart_required`, restart the terminal, rerun `doctor`, then retry `start`/`init`. |
| `forgebadger doctor` is run against a new state path. | The installation has not been initialized yet. | Expect `(not initialized)` plus diagnostic default URLs and dependency results. Confirm the state path is still absent afterward. | No recovery is needed. `doctor` is read-only and must not create a directory, config, secrets, database, or account-recovery key. Run `start` only after the platform terminal runtime is ready. |
| Claude Code session creation fails, the browser terminal opens but the CLI command is not found, or the wrong Claude Code version appears. | Claude Code is missing, not on `PATH`, shadowed by another binary, or too old for the expected prompt behavior. | Run `command -v claude` and `claude --version` in the same shell used to start ForgeBadger. Compare with the path shown by `forgebadger doctor` if available. | Install or update Claude Code, then restart ForgeBadger from a shell where `claude` resolves correctly. If multiple versions exist, put the intended binary earlier on `PATH`. |
| OpenCode or Codex checks fail during exploration, but Claude Code works. | Optional OpenCode/Codex CLIs are not installed. They are non-blocking for the A-stage Claude Code trial path. | Run `opencode --version` and `codex --version`. | Continue the Claude Code trial. Install OpenCode or Codex only if you are testing those optional adapters. Do not treat missing optional CLIs as a first-user trial blocker. |
| Codex native login shows `not_authenticated`, `cli_missing`, or `unknown`. | Codex login is Codex-owned; ForgeBadger does not own the login token and sessions always launch with host-environment credentials. | As the instance administrator, run `codex login status` in the same host environment. Record only normalized state/method. | Complete the official `codex login` flow in a terminal or install/fix Codex. Never paste `auth.json` content, keyring content, raw status output, or tokens into diagnostics. |
| `apply-provider` preview or apply fails, or the CLI still uses the old provider after apply. | The caller is not instance admin, the selected provider/model/credential id is invalid, or the CLI config file could not be written atomically. | Rerun `POST /api/v1/cli-config/:adapter/apply-provider/preview` and check the masked diff and error message; confirm the target config path is writable by the Gateway user. | Fix the reported cause, then rerun apply-provider and restart the session. Use `/apply-provider/rollback` to restore the AES-256-GCM-encrypted backup if an apply left the CLI config in a bad state. |
| A stopped session starts without the previously configured provider/model. | Expected: sessions are model-agnostic and always restart as plain host-environment sessions; there is no frozen launch environment to restore. | Confirm the CLI's global config currently contains the intended provider (`~/.claude/settings.json`, `~/.codex/config.toml` + `~/.codex/auth.json`, `opencode.json`, or `~/.kimi-code/config.toml`). | Re-run `apply-provider` for that adapter to write the intended provider/model/credential into the CLI's global config, then restart the session. |

## Startup And Loopback

| Symptom | Likely cause | Check | Fix or workaround |
| --- | --- | --- | --- |
| Gateway or Web startup fails with `EADDRINUSE`, health checks hit another process, or the browser opens the wrong app. | Loopback port conflict on the trial ports. | Check the configured ports, then run `curl --noproxy '*' -i http://127.0.0.1:48731/api/v1/health` and `curl --noproxy '*' -i http://127.0.0.1:48732/login`. | Stop the conflicting process or restart ForgeBadger with different Gateway and Web ports. For source fallback, keep `FORGEBADGER_GATEWAY_URL` and `NEXT_PUBLIC_GATEWAY_URL` aligned with the Gateway port. |
| Gateway or Web cannot bind `127.0.0.1`, or Chrome/Playwright cannot connect from the test process. | Restricted environment, sandbox, container networking, or loopback binding policy. | Confirm the exact bind host and port in startup logs. Run the two `curl --noproxy '*'` checks from the same environment that will open the browser or run Playwright. | Use a normal local shell with loopback access. If a container is required, expose and map the Gateway and Web ports explicitly and keep browser checks inside the same network namespace. |
| Health checks fail only when normal `curl` is used, or they appear to go through an unrelated proxy. | Proxy environment variables are intercepting loopback requests. | Run `env | rg -i 'proxy'` and compare normal `curl` with `curl --noproxy '*'`. | Use `curl --noproxy '*'` for local ForgeBadger checks. If needed, add `127.0.0.1,localhost` to `NO_PROXY` for the shell that starts ForgeBadger. |
| Chrome/Playwright fails to launch or Next/Turbopack fails with `Operation not permitted`. | Sandbox limits prevent browser launch, worker process creation, socket operations, or Turbopack internals. | Read the first failing log line and confirm whether it mentions Chrome, Playwright, Next, Turbopack, or `Operation not permitted`. | Treat this as an environment limitation first. Re-run in a less restricted shell or CI profile. For local Web startup, try the documented Next command from the runbook and capture the full error if it still fails. |

## Automation Boundary

If automated tests pass but the user still sees a terminal failure, prefer the
manual evidence path over the CI result. Unit tests and mocked Playwright can
prove API contracts and Web safety boundaries, but they do not prove physical
host tmux behavior, native Windows ConPTY/psmux behavior, real browser terminal
input/output, real Claude Code permission prompts, or native Windows versus WSL
terminal support.

## Secrets And State

| Symptom | Likely cause | Check | Fix or workaround |
| --- | --- | --- | --- |
| Gateway refuses to start, login tokens fail after restart, encrypted values cannot be read, or logs mention `FORGEBADGER_MASTER_KEY`. | `FORGEBADGER_MASTER_KEY` is missing, malformed, changed between runs, or weaker than expected. | For source fallback, inspect the environment without printing secrets into shared logs. The preferred value is a 64-character hex key from `openssl rand -hex 32`. | Set a stable `FORGEBADGER_MASTER_KEY` before starting Gateway. Do not rotate it for an existing database unless you are intentionally discarding encrypted local trial state. |
| Gateway refuses to start, authentication fails, or logs mention `FORGEBADGER_JWT_SECRET`. | `FORGEBADGER_JWT_SECRET` is missing, too short, or changed between Gateway restarts. | Confirm the variable is present in the same shell that starts Gateway. Use a random value with at least 32 characters for source fallback. | Set a stable `FORGEBADGER_JWT_SECRET` and restart Gateway. Existing browser sessions may need logout/login after a secret change. |
| Gateway starts but account creation, project creation, or session creation fails with a Database write error. | Database path is not writable, parent directory does not exist, or file permissions belong to another user. | Check `FORGEBADGER_DB_PATH`, then run `test -w "$(dirname "$FORGEBADGER_DB_PATH")"` for source fallback. For npm/CLI startup, check the active state directory. | Create the parent directory, fix ownership/permissions, or set `FORGEBADGER_DB_PATH` to a writable local path such as `/tmp/forgebadger-trial/forgebadger.db` for disposable source fallback. |
| 登录页提示密码错误且无法进入应用。 | 本地账户密码遗失。 | 在启动 ForgeBadger 的同一台主机上打开“Forgot password”，并从 Gateway 启动日志确认恢复密钥路径；默认是 `~/.forgebadger/account-recovery.key`，迁移安装或自定义状态目录以日志为准。 | 复制文件内容作为 recovery key，填写账户邮箱和新密码。成功后密钥会立即轮换、所有旧会话失效，需用新密码正常登录。恢复接口只接受直接 loopback 请求，不能经反向代理或端口转发调用。不要把密钥贴到日志、Issue 或聊天中。 |
| Source fallback ignores an intended disposable database or port override. | The shell running Gateway/Web may not actually contain the prefixed variable, or another terminal is still running an older process. | Start Gateway with an explicit prefix such as `FORGEBADGER_DB_PATH=/tmp/forgebadger-trial/forgebadger.db pnpm --dir packages/gateway dev`, then confirm the target file is created. | Restart the affected Gateway/Web process. Current source scripts preserve command-prefix env over root `.env`; if the override still does not apply, verify the command was run from a fresh shell and that no old process is serving the port. |
| npm trial shows old users, old projects, unexpected defaults, or stale sessions. | The npm/CLI trial is reusing existing default state, usually under `~/.forgebadger` or the configured `FORGEBADGER_STATE_DIR`. | Check startup logs for the state directory. Inspect whether `FORGEBADGER_STATE_DIR` is set. | Use a disposable `FORGEBADGER_STATE_DIR` for a fresh trial. Do not delete `~/.forgebadger` unless you intentionally want to remove all local ForgeBadger trial state. |

## Terminal And WebSocket

| Symptom | Likely cause | Check | Fix or workaround |
| --- | --- | --- | --- |
| Browser terminal fails to connect, reconnect loops, or Network shows WebSocket 401/403. | WebSocket auth token is missing, expired, or belongs to another local state/database. | In browser devtools, inspect the `/ws/terminal/:sessionId` request status. Log out and log back in, then retry the same session. | Refresh auth by logging in again. Confirm Web and Gateway point to the same Gateway URL and database state. If using source fallback, verify `NEXT_PUBLIC_GATEWAY_URL` matches the running Gateway. |
| Terminal attach fails after session creation, or output is blank even though the session exists. | Multiplexer session name mismatch, session exit, pty attach failure, or CLI failure before output capture. | Inspect Gateway logs and run `tmux list-sessions`/`tmux capture-pane ...` on macOS/Linux/WSL or the equivalent `psmux` commands on native Windows. | Reopen the terminal from the session page. If the multiplexer session is gone, create a new session. If the pane shows CLI startup errors, fix the underlying CLI or project path issue first. |
| macOS with a pnpm install: every terminal attach reports `Terminal attach failed: posix_spawnp failed`, even when the tmux session exists and `tmux` is on `PATH`. | node-pty 1.1.0 ships the darwin prebuild `spawn-helper` without the execute bit (644). pnpm's content-addressable store preserves tarball permissions, so `node-pty` cannot exec its helper and every spawn fails at the native layer. Fixed upstream in the node-pty 1.2.0-beta line (microsoft/node-pty#850). | Run `node -e "const {spawn}=require('node-pty');const p=spawn('/bin/echo',['hi'],{cwd:'/tmp'});p.onExit(()=>{process.exit(0)});"` — any `posix_spawnp failed` confirms it. Check `ls -la node_modules/.pnpm/node-pty@*/node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper`. | Rerun `pnpm install`; the repo postinstall (`scripts/fix-node-pty-helper.mjs`) chmod +x's the helper idempotently. Remove that script once node-pty is upgraded past the fixed release. |
| Reopening a session does not show recent terminal history. | Multiplexer `capture-pane` cannot read the pane, the pane has no scrollback, or the wrong target is used. | Run the selected runtime's `capture-pane -e -S -500 -t <session-name>` and confirm whether expected history appears outside ForgeBadger. | Keep the multiplexer session running and retry attach. If capture output is empty outside ForgeBadger too, collect runtime status and Gateway logs; history comes from tmux/psmux, not SQLite. |
| 「同步模型」提示 `Private or loopback network addresses are not allowed`，且本机任意域名的 DNS 都解析为 198.18.0.x。 | Surge/Clash 类代理的 fake-ip 模式把所有域名解析到 198.18.0.0/15（RFC 2544 基准测试段）；网关出站防护已放行该段（公网不可路由、非真实内网，无 SSRF 风险），老版本会误拒。 | 运行 `dig +short api.openai.com`，看是否返回 198.18.x.x。 | 更新/重启 Gateway 到放行 198.18/15 的版本后重新同步；不要关闭代理或修改代理 DNS 设置。 |
| Opening the same terminal in a second browser tab disconnects the first tab. | ForgeBadger allows one active WebSocket per terminal session; the newest terminal connection replaces the previous one. | Watch the first tab when opening the same session in a second tab. Check Gateway logs for replacement or disconnect messages. | Use one active browser terminal per session. If you need side-by-side work, create a separate ForgeBadger session instead of attaching the same terminal twice. |
| Browser close, refresh, or Gateway restart appears to leave CLI work running. | This is expected multiplexer persistence. Browser and Gateway lifecycle should not kill the underlying CLI session by itself. | Close the browser or stop Gateway, then list sessions with tmux or psmux. Restart Gateway/Web and reopen the session. | Treat this as normal persistence. Stop the session from Web when you intend to end it; kill a multiplexer session manually only after confirming it is no longer needed. |
| OpenCode permission requests never appear as ForgeBadger notifications. | The ForgeBadger plugin is missing from the project `.opencode/plugins/`, the session was already running before the plugin was materialized, the launch env vars are not injected, or the plugin write was blocked. | Check that `.opencode/plugins/forgebadger-permission-notify.js` exists in the project (Gateway materializes it on OpenCode session create/restart). Confirm `FORGEBADGER_GATEWAY_URL`, `FORGEBADGER_SESSION_ID`, and `FORGEBADGER_ATTACH_TOKEN` are present in the tmux launch env (the plugin reads them at load). | Restart the OpenCode session so the plugin is (re)materialized and reloaded. If the file is missing, check Gateway logs for `[opencode-notification-settings]` warnings — a `safeResolve` rejection (e.g. `.opencode` symlinked outside the project) or a plugin read/write failure is non-fatal and silently skips notification reporting. |

## Skill Discovery

| Symptom | Likely cause | Check | Fix or workaround |
| --- | --- | --- | --- |
| Skill Discovery shows unexpected local sources or more Skill roots than the first-user trial needs. | Local Skill discovery should default to `${CLAUDE_CONFIG_DIR:-~/.claude}/skills` and `${AGENTS_HOME:-~/.agents}/skills`, plus any explicit `FORGEBADGER_SKILL_DIRS` override. In the root-owned trial server those defaults appear as `/root/.claude/skills` and `/root/.agents/skills`. | In the Skills page or diagnostics output, compare displayed roots with the expected A-stage roots and inspect `FORGEBADGER_SKILL_DIRS`, `CLAUDE_CONFIG_DIR`, and `AGENTS_HOME` in the Gateway startup environment. | Remove unintended `FORGEBADGER_SKILL_DIRS` entries or start Gateway with the intended Claude/Agents home directories. Include the displayed roots in feedback if stale Skill rows remain after local rescan. |
